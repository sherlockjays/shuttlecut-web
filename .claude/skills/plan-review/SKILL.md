# 계획 리뷰

계획을 세운 세션은 자기가 고른 방법 안에서만 생각한다. 그래서 문제만 아는 세션이 먼저 해법을 따로 내고, 그다음 세션이 그것과 계획을 견준다. 세션을 둘로 나누는 이유는 첫 세션이 계획을 볼 방법을 아예 없애기 위해서다.

이 스킬은 승인하거나 반려하지 않는다. 무엇을 택할지는 사용자가 정한다.

## 1. 입력 정하기

받은 인자: $ARGUMENTS

- **이슈 번호**: 인자에 있으면 그것을 쓴다. 없으면 브랜치 이름(`*/issue-NN`)이나 계획 제목에서 찾는다. 그래도 없으면 사용자에게 묻는다
- **계획 파일**: 인자에 경로가 있으면 그것을 쓴다. 없으면 `~/.claude/plans/`에서 가장 최근에 수정된 파일을 쓰고, 어느 파일을 골랐는지 사용자에게 알린다
- **의도와 제약**: 계획 맨 위에 이 절이 있으면 2단계의 기준이 된다. 없어도 멈추지 않고 이슈 본문을 기준으로 진행한다

저장소 밖 임시 폴더를 하나 정하고 계획 파일을 그 안에 복사한다. 두 세션의 결과도 여기에 둔다. 저장소 안에 두면 추적되지 않는 파일이 생긴다.

## 2. 넘길 문장은 고정이다

아래 두 문장을 그대로 쓰고 `<...>`만 채운다. 이 세션의 맥락, 계획을 세우며 내린 판단, "특히 여기를 봐줘"를 덧붙이지 않는다. 덧붙이면 리뷰어가 그 판단을 따라간다.

계획에 "의도와 제약" 절이 있으면 그 절의 본문만 1단계 문장 끝에 `의도와 제약: <본문>`으로 덧붙인다. 사용자가 준 조건이지 이 세션의 판단이 아니기 때문이다. 계획의 다른 부분은 1단계에 넘기지 않는다.

### 1단계: 문제만 읽고 해법 후보 내기

```
이슈 #<번호>를 읽고(gh issue view <번호>) 관련 코드를 확인한 뒤, 이 문제를 푸는 방법 후보를 두세 개 내줘. 후보마다 무엇을 바꾸는지, 얻는 것, 잃는 것, 어떤 전제에서 가장 좋은 선택인지 적어줘. 마지막에 네가 고른다면 어느 것인지와 이유를 한 단락으로 적어줘. 구현하지 말고, 파일과 메모리는 수정하지 말고, 결과만 출력해줘.
```

### 2단계: 후보와 계획 비교하기

```
계획을 검토해줘. 읽을 것은 세 가지야. (1) 계획 파일 <임시 폴더>/plan.md (2) 계획을 보지 않은 다른 세션이 같은 문제에 대해 독립적으로 낸 해법 후보 <임시 폴더>/candidates.md (3) 이슈 #<번호> (gh issue view <번호>). 계획 맨 위에 '의도와 제약'이 있으면 저장소의 현재 모습이 아니라 그것을 기준으로 판단하고, 없으면 이슈 본문을 기준으로 해. 아래 여섯 항목을 순서대로 적어줘. 해당 사항이 없으면 '없음'이라고만 적어. 1. 계획이 고려하지 않은 대안: 독립 후보에는 있는데 계획이 다루지 않은 방법, 그리고 그것이 계획의 선택보다 나을 수 있는 조건. 2. 선택이 기대는 전제: 계획의 방법이 옳으려면 참이어야 하는 것과, 그것이 깨지는 조건. 3. 코드와 다른 주장: 계획이 기존 코드에 대해 말한 것(어디서 쓰인다, 어떻게 동작한다) 중 실제 코드와 다른 것. 반드시 해당 파일을 직접 열어 확인해. 4. 빠진 짝: CLAUDE.md의 '두 곳을 같이 고쳐야 하는 것'과 '깨지기 쉬운 계약' 중 계획이 건드리는데 다루지 않은 것. 5. 커밋 순서: 각 커밋이 단독으로 빌드와 테스트를 통과하지 못할 지점. 6. 더 작은 방법: 의도한 결과를 그대로 내면서 덜 바꾸는 방법이 있는 부분. 변화가 크다는 이유만으로 과하다고 하지 마. 승인이나 반려 같은 판정은 내리지 말고, 문체나 표현도 다루지 마. 구현하지 말고, 파일과 메모리는 수정하지 말고, 결과만 출력해줘.
```

"변화가 크다는 이유만으로 과하다고 하지 마"는 지우지 않는다. 새 라이브러리를 들이거나 컨벤션 자체를 다시 짜는 것이 의도일 때가 있다.

## 3. 실행

화면 없는 세션(`claude -p`)으로 순서대로 띄운다. 1단계가 끝나야 2단계를 띄울 수 있다. 읽기와 조회만 허용한다.

```bash
# 1단계
claude -p "<1단계 문장>" \
  --allowedTools "Read" "Grep" "Glob" \
    "Bash(git log *)" "Bash(git show *)" "Bash(git diff *)" "Bash(gh issue view *)" \
  --output-format text > <임시 폴더>/candidates.md 2> <임시 폴더>/candidates.err

# 2단계. 임시 폴더를 읽을 수 있게 --add-dir로 연다
claude -p "<2단계 문장>" --add-dir <임시 폴더> \
  --allowedTools "Read" "Grep" "Glob" \
    "Bash(git log *)" "Bash(git show *)" "Bash(git diff *)" "Bash(gh issue view *)" \
  --output-format text > <임시 폴더>/review.md 2> <임시 폴더>/review.err
```

- Windows의 Git Bash에서는 `claude` 대신 `claude.cmd`로 부른다. 경로는 `C:/...` 형태로 넘긴다
- 1단계는 1~2분, 2단계는 2분쯤 걸린다. 백그라운드로 돌리고 끝나면 이어간다
- 실패했거나 결과가 비어 있으면 `.err` 파일을 읽고 사용자에게 알린다. 이 세션이 대신 검토하지 않는다

## 4. 결과 전달

1. 1단계의 후보를 표로 요약한다: 후보, 내용, 가장 좋은 조건, 1단계 세션이 고른 것
2. 2단계의 여섯 항목을 **고치지 않고** 그대로 보여준다. 줄이거나 순서를 바꾸지 않는다. 계획을 세운 세션이 걸러내면 불리한 지적부터 빠진다
3. 그 아래에 "계획을 세운 쪽의 의견"이라고 구분해서, 지적마다 동의하는지와 근거를 짧게 적는다. 코드를 다시 열어 확인한 것과 확인하지 않은 것을 구분한다

**여기서 멈춘다.** 계획을 고치지 않는다. 무엇을 반영할지 사용자가 정한 뒤에 고친다.
