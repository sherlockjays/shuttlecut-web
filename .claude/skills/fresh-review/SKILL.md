# 새 세션 리뷰

작업한 세션은 자기 판단에 끌려 자기 코드를 너그럽게 본다. 그래서 리뷰는 이 대화를 모르는 새 세션이 하고, 이 세션은 그 결과를 받아 반영 여부만 따진다.

## 1. 대상 정하기

받은 인자: $ARGUMENTS

위 인자에 PR 번호가 있으면 그것을 쓴다. 비어 있으면 현재 브랜치의 PR을 찾는다.

```bash
gh pr view --json number -q '.number'
```

PR이 없으면 멈추고 사용자에게 알린다. 반영할 지적을 PR 코멘트로 남기는 흐름이라 PR이 있어야 한다.

바뀐 경로로 어떤 리뷰를 돌릴지 정한다.

```bash
gh pr diff <번호> --name-only
```

| 바뀐 경로 | 돌릴 리뷰 |
| --- | --- |
| `frontend/` | `frontend-code-review` |
| `backend/` | 내장 `code-review`. 백엔드 전용 리뷰 스킬이 생기기 전까지 쓴다 |
| 둘 다 | 둘 다, 동시에 |
| 둘 다 아님 | 내장 `code-review` |

## 2. 새 세션에 넘길 문장

**아래 문장을 그대로 쓴다. 이 세션의 맥락을 덧붙이지 않는다.** "특히 여기를 봐줘"나 작업 중 내린 판단을 넣으면 리뷰어가 그 판단을 따라간다. 의도와 결정 근거는 PR 본문에 있고 리뷰어가 직접 읽는다.

PR에 리뷰 코멘트가 이미 있는지로 라운드를 가른다.

```bash
gh api "repos/{owner}/{repo}/pulls/<번호>/comments" -q 'length'
```

**1라운드(코멘트 0개)**

```
/frontend-code-review #<번호> PR 본문과 관련 메모리 및 변경사항 확인하고 리뷰해줘. 파일과 메모리는 수정하지 말고, PR에 코멘트도 달지 말고, 리뷰 결과만 출력해줘.
```

**2라운드 이후(코멘트 1개 이상)**: 위 문장 끝에 덧붙인다.

```
PR에 달린 리뷰 코멘트도 읽고, 그 지적이 이후 커밋에서 해결됐는지 확인해줘.
```

백엔드 리뷰는 맨 앞의 `/frontend-code-review #<번호>`를 `/code-review <번호>`로 바꾼다. 노력 수준은 적지 않는다.

## 3. 새 세션 실행

화면 없는 세션(`claude -p`)으로 띄운다. 확인 창을 띄울 수 없는 세션이라 읽기와 조회 명령을 미리 허용한다. 쓰기 도구는 허용하지 않는다. 허용하면 리뷰어가 메모리 파일을 고친다.

```bash
claude -p "<2의 문장>" \
  --allowedTools "Read" "Grep" "Glob" "Agent" "Skill" \
    "Bash(git diff *)" "Bash(git show *)" "Bash(git log *)" "Bash(git status *)" \
    "Bash(git rev-parse *)" "Bash(git merge-base *)" "Bash(git symbolic-ref *)" \
    "Bash(gh pr view *)" "Bash(gh pr diff *)" "Bash(gh pr checks *)" \
    "Bash(gh issue view *)" "Bash(gh api *)" \
    "Bash(npm run lint)" "Bash(npm run test)" "Bash(npm run build)" \
  --output-format text > <결과 파일> 2> <결과 파일>.err
```

- Windows의 Git Bash에서는 `claude` 대신 `claude.cmd`로 부른다. `claude`는 실행되지 않는다
- 결과 파일은 저장소 밖 임시 폴더에 둔다. 저장소 안에 두면 추적되지 않는 파일이 생긴다
- 프론트 리뷰는 5분, 백엔드 리뷰는 3분쯤 걸린다. 백그라운드로 돌리고 끝나면 이어간다. 기다리는 동안 다른 일을 하지 않는다
- 프론트와 백엔드를 둘 다 돌릴 때는 결과 파일을 따로 두고 동시에 띄운다

실패했거나 결과 파일이 비어 있으면 `.err` 파일을 읽고 사용자에게 알린다. 이 세션이 대신 리뷰하지 않는다.

## 4. 결과 검토와 제안

결과 파일을 읽는다. 앞부분에 진행 상황을 알리는 문장이 섞여 있을 수 있다.

결과에 "스킬이 빈 결과를 돌려줘서 직접 읽었다"는 식의 문장이 있으면 리뷰 스킬이 돌지 않은 것이다. 그 결과를 쓰지 않고 사용자에게 알린다. 변경이 아주 작은 PR에서 내장 `code-review`가 이렇게 끝난 적이 있다.

지적마다 실제 코드를 열어 확인한 뒤 반영 여부를 제안한다. 리뷰어의 말을 그대로 옮기지 않는다.

| 지적 | 리뷰어 판정 | 제안 | 이유 |
| --- | --- | --- | --- |
| 한 줄 요약 | CONFIRMED / PLAUSIBLE / 없음 | 반영 / 기각 / 별도 이슈 | 코드에서 확인한 근거 |

- 재현되지 않는 시나리오는 기각을 제안한다
- 이 PR의 범위를 벗어나는 지적은 별도 이슈를 제안한다
- 동작 결함(실패 시나리오가 확인된 것)이 하나도 없으면 "이번 라운드로 종료"를 제안한다. 지적이 0개가 될 때까지 돌리지 않는다. 문제를 찾으라고 시킨 리뷰어는 늘 뭔가를 찾는다

**여기서 멈춘다.** 반영 여부는 사용자가 정한다.

## 5. 반영하기로 한 지적을 PR 코멘트로

사용자가 반영하기로 한 지적만 남긴다. 기각한 지적은 PR에 적지 않는다.

1. 코멘트 본문 초안을 채팅에 보여주고 확인을 받는다
2. `~/.claude/skills/frontend-code-review/references/posting-comments.md`의 형식과 규칙을 따라 해당 줄에 단다. 줄 번호는 그 문서의 방법으로 다시 계산하고, 계산한 줄에 지적이 인용한 코드가 있는지 확인한다
3. 줄을 특정할 수 없으면 일반 코멘트로 단다
4. 단 코멘트의 URL을 알린다

`gh pr review --approve`와 `--request-changes`는 쓰지 않는다. 승인은 사람이 한다.

코멘트를 단 뒤 수정 계획을 세운다. 수정이 끝나면 이 스킬을 다시 불러 다음 라운드를 돌린다.
